# 第一版架构

## 设计选择

Electron 负责 Windows 原生窗口与离线静态页面加载；React 负责交互。主进程关闭 Node 集成、启用上下文隔离和进程沙盒，拒绝新窗口、页面导航与权限申请。生产 CSP 不允许远程脚本；仅开发服务器允许 React 刷新所需的内联脚本。

v0.3 通过固定 IPC 接入识别服务：设置、原生目录选择、联盟窗口列表、预览、立即扫描与观察事件。验证发送窗口和主 frame；渲染层不能任意读取文件、请求任意本机地址或执行命令。服务仅 GET 本机 127.0.0.1 上白名单 LCU 与 Live Client Data 路径，不读取游戏内存。

## 状态与持久化

`Session` 包含英雄 ID、实际已选、至多三个候选、等级、已有装备、敌方压力、偏好和可选的手动流派锁定。每次变更经过 `sanitizeSession` 校验。应用使用 localStorage 保存小型单局状态；尚无历史查询需求，因此暂不引入 SQLite 原生依赖。未来复盘再引入带迁移的数据库。

更换英雄清空本局状态并保留偏好；新一局保留英雄与偏好。损坏或未知字段被过滤，存储异常有可见提示。

## 推荐流程

1. 根据英雄种子路线的基础权重开始比较。
2. 已选海克斯按标签为路线提供匹配分；缺少触发条件的强化不参与该项加分。
3. 技能暴击路线在缺少关键机制时降权；盖伦自有机制另行处理。
4. 已有核心装备提供继续路线的倾向，减少无成本转型假设。
5. 偏好对承伤、成长和实验路线提供有限调整。
6. 候选逐个在复制的状态上模拟，绝不改变实际路线。
7. 手动锁定优先用于本局输出，但候选仍提示其他可能的方向。
8. 按实际等级生成 1–18 级合法加点，终极技能在 6/11/16 级提升。

规则分数是内部排序，不代表经过统计校准的收益或胜率。第一版未实现全装备冲突矩阵、经济模拟与实际技能点输入。

## 扩展接口

`recognition` 服务输出带实例 ID、递增序号、时间和来源的观察；纯函数协调器去除过期/乱序事件，要求连续两次稳定，限制海克斯大乱斗模式，并保留手动纠错锁。OCR 候选只能更新候选区；只有独立已选区域的读数能增加已选强化。图标匹配同时要求绝对相似度与次优差距，不把共用图标当成可靠结论。

OCR worker 与语言模型只从本地安装资源加载。窗口捕获限定联盟标题，不捕获整个桌面；预览仅用户主动打开，截图默认不落盘。LCU 口令仅留在主进程内存；对局账户名称只用于在响应中定位自己，不向界面或文件输出。配置位于应用 userData/recognition.json；本局和纠错锁保存在 localStorage。详见 [识别说明](RECOGNITION.md)。

知识包未来采用 JSON Schema 与独立校验、签名；当前作为 TypeScript 内容模块在构建时打包，修改后需重新构建。
